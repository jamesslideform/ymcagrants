# Data model — DynamoDB (proof of concept)

Matches the whiteboard from the kickoff: a grant form that writes to DynamoDB, and an
"outcomes by zip" view that reads back out of it.

Deliberately small. One table, two item types, one secondary index. If something here is
wrong, change it in a PR — `docs/api-contract.md` and `frontend/src/types.ts` move with it.

## Table: `ymcagrants`

Single table, on-demand billing. Two item types share it so a grant and its outcomes come
back in one query.

| Attribute | Purpose |
| --- | --- |
| `pk` | Partition key |
| `sk` | Sort key |
| `gsi1pk` / `gsi1sk` | Secondary index — see access patterns |
| `entityType` | `"grant"` or `"outcome"`, so code never guesses from the key |

### Grant item

```
pk      = "GRANT#<grantId>"
sk      = "METADATA"
gsi1pk  = "GRANTS"
gsi1sk  = "<submissionDate>#<grantId>"
```

| Attribute | Type | Notes |
| --- | --- | --- |
| `grantId` | `S` | UUID generated by the backend |
| `name` | `S` | |
| `funder` | `S` | Plain text for the PoC — no separate funder record yet |
| `status` | `S` | `prospect`, `submitted`, `active`, `closed`, or `declined` — drives the overview breakdown |
| `submissionDate` | `S` | `YYYY-MM-DD` |
| `startDate` | `S` | `YYYY-MM-DD`, nullable |
| `lengthMonths` | `N` | How long the grant runs, nullable |
| `dueDate` | `S` | `YYYY-MM-DD`, nullable — the reporting deadline |
| `amountRequested` | `N` | nullable |
| `amountReceived` | `N` | nullable — empty until the award lands |
| `createdAt` | `S` | ISO-8601 |

### Outcome item

```
pk      = "GRANT#<grantId>"
sk      = "OUTCOME#<outcomeId>"
gsi1pk  = "ZIP#<zipCode>"
gsi1sk  = "<createdAt>#<outcomeId>"
```

| Attribute | Type | Notes |
| --- | --- | --- |
| `outcomeId` | `S` | UUID |
| `grantId` | `S` | The grant this outcome reports against |
| `peopleServed` | `N` | The number every funder asks for |
| `socialStatus` | `S` | A **category** ("youth", "seniors", "families"), nullable |
| `zipCode` | `S` | The "locale" on the whiteboard; drives the by-zip view |
| `descriptionOfFunding` | `S` | What the money paid for, nullable |
| `result` | `S` | What happened, in the grants manager's words, nullable |
| `createdAt` | `S` | ISO-8601 |

## Access patterns

Every screen in the PoC maps to one of these. Nothing here needs a `Scan`.

| Need | Operation |
| --- | --- |
| Save a grant from the form | `PutItem` on the grant item |
| List all grants (newest first) | `Query` GSI1 where `gsi1pk = "GRANTS"`, `ScanIndexForward: false` |
| Filter by status, or search name/funder | Filter the GSI1 query in the handler — the grant count stays small enough that a dedicated index isn't worth it yet |
| Overview totals and status counts | Aggregate that same grant query plus the outcomes, in the handler |
| One grant with its outcomes | `Query` main table where `pk = "GRANT#<id>"` |
| Record an outcome | `PutItem` on the outcome item |
| **Outcomes by zip** | `Query` GSI1 where `gsi1pk = "ZIP#<zip>"` |
| Every zip, for the summary | `Query` GSI1 per known zip, or aggregate in the handler for the PoC |

The last one is the honest soft spot: with a weekend's worth of data, the handler can read
the outcomes and group them in memory. If this ever holds real volume, keep a running total
per zip in its own item rather than reaching for a `Scan`.

## Why DynamoDB here, and what it costs us

It's the team's AWS stack and it gets a working demo up fastest — no migrations, no
instance to provision. Worth naming the trade so nobody is surprised later:

- **Ad-hoc analysis is harder.** "Outcomes by program by quarter" is a SQL `GROUP BY`; here
  it's either a planned index or application code. The PoC only promises by-zip.
- **Outcome questions are fixed.** The product deck models outcome questions as *data* — a
  measure library, so a new funder question is a form entry rather than a migration. This
  PoC hard-codes the six fields on the whiteboard instead. That's the right call for a
  one-day demo and the first thing to revisit after it, because "how many kids were
  positively affected?" is one funder's phrasing of a question the next funder will ask
  differently.
- Schemaless storage makes that revisit cheap on the write side: adding a flexible
  `measures` collection later is new item types, not an `ALTER TABLE`.

## Privacy

No item above holds a client name, address, date of birth, or case note. `socialStatus` is
a category and `peopleServed` is a count. Outcome rows describe a group in a zip code, not
a person — keep it that way, and if a funder asks for client-level reporting, that's a
conversation with Kelly before it is an attribute.
